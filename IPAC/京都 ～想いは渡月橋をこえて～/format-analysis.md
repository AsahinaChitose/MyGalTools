# 《京都 ～想いは渡月橋をこえて～》封包与位图字体分析

本文记录汉化过程中对 `kyoto.exe`（73,728 字节，ImageBase 0x400000，4 个节）的静态逆向结果，
以及由此得到的 `.PAK` 封包与 `IEF24M.IFD` 位图字体格式。所有地址均为 VA（基址 0x400000 固定，无重定位）。

分析工具：IDA 9.1 + Hex-Rays；验证方式：反编译阅读 + 对三个原始封包做解包/重封逐字节比对 + 字体字模抽样。

---

## 1. 文件一览

| 文件 | 内容 |
|---|---|
| `DATA\SCR.PAK` | 脚本封包，57 个 `.SCN` 文本脚本 |
| `DATA\CHR.PAK` | 人物立绘封包，54 个 `.IES` |
| `DATA\BG.PAK` | 背景图封包，130 个 `.IES` |
| `DATA\IEF24M.IFD` | 位图字体（IEF Font Data，24px） |
| `SYSFLAG.DAT` / `DATA\DATxxxx.DAT` | 存档/系统标志，与本文无关 |

游戏用 `IsDBCSLeadByte` 判断双字节字符、用自绘 8bpp 位图字体渲染文本，文本编码由系统 ANSI 代码页决定。

## 2. PAK 封包（IPAC）

### 2.1 结构

```
+0x00  u32  magic = 'IPAC'（小端 0x43415049）    ; exe 中直接与 0x43415049 比较
+0x04  u16  count                                  ; 条目数
+0x06  u16  version                                ; 三个封包均为 2，加载器不校验
+0x08  TOC[count]，每项 24 字节：
         char name[16]   ASCII，NUL 填充；查找用 lstrcmpiA（不区分大小写）
         u32  offset     绝对文件偏移
         u32  size       存储大小
       数据区紧跟在 TOC 之后（第一个 offset == 8 + 24*count）
```

### 2.2 成员数据

```
+0x00  u32  'IEL1'（0x314C4549）    ; 有该魔数即压缩
+0x04  u32  raw_size                 ; 解压后大小
+0x08  ...  LZSS 压缩流
```

没有 `IEL1` 魔数的成员按原样存储（加载器分支支持，原版封包全部为压缩）。

### 2.3 LZSS 参数与位流

逆向自 `sub_407350`（解压）与打包工具复现：

| 参数 | 值 |
|---|---|
| 环形窗口 | 4096 字节，前 4078 字节初始化为 `0x20`（空格） |
| 最大匹配 | 18 |
| 最小匹配 | 3 |
| 标志位 | 每 8 个 token 一个标志字节，**LSB 优先** |
| bit = 1 | 字面量（1 字节） |
| bit = 0 | 回溯对（2 字节）：`b1` = 偏移低 8 位；`b2` = `((偏移 >> 4) & 0xF0) \| (长度 - 3)` |
| 偏移 | 12 位绝对环形下标，解码时 `& 0xFFF` |
| 终止 | 输出达到 `raw_size` 即停（不依赖输入结束） |

解码伪代码：

```python
buf = bytearray(4096); buf[:4078] = b' ' * 4078
r, flags = 4078, 0
out = bytearray()
while len(out) < raw_size:
    flags >>= 1
    if (flags & 0x100) == 0:
        flags = src[i] | 0xFF00; i += 1
    if flags & 1:                     # 字面量
        c = src[i]; i += 1
        out.append(c); buf[r] = c; r = (r + 1) & 0xFFF
    else:                             # 回溯
        b1, b2 = src[i], src[i+1]; i += 2
        pos = ((b2 & 0xF0) << 4) | b1
        for _ in range((b2 & 0x0F) + 3):
            c = buf[pos & 0xFFF]; pos += 1
            out.append(c); buf[r] = c; r = (r + 1) & 0xFFF
```

### 2.4 相关函数

| VA | 作用 |
|---|---|
| `0x4074D0` | 打开 PAK、读头与 TOC、按名字找条目、读成员、按需解压 |
| `0x407650` | 返回最近一次解压后大小 `dword_41CE4C` |
| `0x407470` | `lstrcmpiA` 线性查找名字，返回下标或 -1 |
| `0x407350` | LZSS 解压 |

### 2.5 复现与验证

`pak_tool.py` 用经典 Okumura 二叉树 LZSS 编码器实现压缩，**压缩结果与原始封包逐字节一致**：

| 封包 | 条目 | 原始大小 | 解压后 | 重封 |
|---|---|---|---|---|
| `scr.pak` | 57 | 207,230 | 420,770 | 字节一致 |
| `chr.pak` | 54 | 12,624,508 | 44,143,416 | 字节一致 |
| `bg.pak` | 130 | 93,592,677 | 158,325,800 | 字节一致 |

重封一致说明压缩器与当年打包工具等价（匹配选择、树更新顺序全部相同），
因此“解包→改文本→重封”不会引入非必要的字节差异。

**加密：无。** 整个封包链路只有这一层 LZSS。

## 3. 位图字体 `IEF24M.IFD`

### 3.1 文件结构

```
+0x0000  u16  字形边长（0x18 = 24）
+0x0002  16384 × u16   SJIS(0x8140 起) → 字形序号表，0xFFFF = 缺字
+0x8002  u32  位图宽  width  = 768   （32 列 × 24px）
+0x8006  u32  位图高  height = 行数 × 24
+0x800A  u32  bpp = 8
+0x800E  ...  调色板等
+0x8414  像素数据（0x8002 + 1044）
```

加载函数 `sub_406640`：读前 `0x8002` 字节到全局缓冲，其余读入 `GlobalAlloc` 的位图缓冲，
并把像素指针（结构 +0x410）设为 `缓冲 + 1044`；`dword_40EAB4 = 首字节 = 24`。

### 3.2 字形网格

- 像素按行存放，行宽 = `width`（768）；
- 每行 32 个 24×24 字模；
- **第 0~1 行留给 ASCII**：半角字符按 12×24 绘制，位置 `(12*(c & 0x3F), 24*(c >> 6))`；
- 双字节字模从**第 4 行**开始：

```
offset = 1044 + 24 * (idx % 32) + 768 * 24 * (idx / 32 + 4)
```

原版字体有 8814 个有效字形，最大序号 7723，位图高度 5880（245 行）。

### 3.3 取字：`sub_406740`

```c
if (code < 0x8140) return 0;
if (code >= 0xA000) {
    if (code < 0xE000) glyph = 颜色值;            // 实际不支持，会画到越界
    else { glyph = table2[code]; if (glyph == 0xFFFF) return 0; }
} else {
    glyph = table1[code]; if (glyph == 0xFFFF) return 0;
}
```

两张表在内存中紧挨着字体头部：`table1` 实际基址 `0x4428E2`（对应 0x8140），
`table2` 基址 `0x4468E2`（对应 0xE000）。代码里写的是 `word_432662[code*2]` /
`word_42A8E2[code*2]`，与“以 0x8140 为基准”只差一个常数偏移。

### 3.4 绘制：`sub_406A30`

- 逐字节扫描，`IsDBCSLeadByte` 判双字节，双字节交给 `sub_406740`；
- 全角步进 24px，半角 12px；
- 换行条件 `x > 526 - 24`（`a4 = dword_40E168 = 526`），换行时 `y += 24`；
- 绘制起点：`x = 56`，`y = 消息 y + 32`（`dword_40E160/E164`），底边 `384`；
- `@` + 数字 = 换色控制码（跳过 2 字节，不占宽度）。

### 3.5 抗锯齿 / 加粗算法

`sub_406740` 把 8bpp 源字模转换成 32bpp 临时面的 **alpha**，再画两遍（`+1,+1` 与 `0,0`）形成描边：

- 源像素非 0：`a = 200`；上方有墨则 `216`；其余 8 邻域每有一个非 0 就 `+16`，上限 255；
- 源像素为 0 但有左右邻墨：`a = 32`；上方有墨则 `64`；下方 `+32`；四角各 `+16`；
- **只处理 1..22 的内圈**，最外 1 圈恒为 0 → 字模四周必须留 1px 空白。

由此可以解释两个现象：TTF 渲染的浅抗锯齿外圈会被当成实心笔画（显得又粗又糊），
所以重建字体时要按阈值二值化；并且字模不能触到 24×24 的边缘。

### 3.6 GBK 化方案

原版只认 Shift-JIS。汉化采用“序号直通”方案，避免重建映射表：

```
idx = 190 * (lead - 0x81) + (trail - 0x40) - (trail > 0x7F)
0 <= idx < 23940 ? glyph = idx : 缺字
```

- 23940 = 126 前导 × 190 尾字节；
- 把 `sub_406740` 开头 0x55 字节的双表查找整段 `jmp` 到 `.text` 尾部空白区（`0x40CF68`），
  新代码 89 字节算完序号后跳回 `0x406795`；
- 字体按同一序号重排：ASCII 用的前 4 行从原版拷贝，其后是 23940 个 GBK 槽位，
  高度 `(4 + ceil(23940/32)) * 24 = 18072`（753 行），文件约 13.9 MB。

坑：第一版 cave 用 `movsx ecx, cl` 取序号低位，`cl >= 0x80` 时被符号扩展成负数，
导致 7812/23940 个码位序号偏 -256，表现为约三分之一的字正确、其余乱码。改 `movzx` 后 0 处不一致。

经验值：原版字模墨迹约 19×19、86 个像素；用宋体 20~22px + 阈值 96 重建后密度接近，
标点（`，` `。`）不会退化成点。

## 4. 文本排版与“21 字换行点”

### 4.1 两套行数算法

同一条消息（连续文本行会被引擎用 `0x0A` 合并成一条）分别经过：

- **排版** `sub_4025C0`：按**字节**计，`v3 >= (2*526-16)/24 = 43` 时 `v4++`，
  每条消息末尾 `y += v4 * 24 + 6`；
- **绘制** `sub_406A30`：按**像素**计，`x > 502` 时换行（即每行 21 个全角字）。

### 4.2 边界 bug

一条文本行正好 **21 个全角字**（42 字节）时：

- 排版：42 < 43 → 记 1 行；
- 绘制：第 21 个字画完 `x = 504 > 502`，先换一行，紧接着的 `0x0A` 又换一行 → 实际用了 2 行。

多出来的一行导致下一条消息被画高 24px，压到上一句上；同时那个空行就是它留下的痕迹。
42 字（两行）同理。原版脚本每行都 ≤20 字，所以从未触发。

### 4.3 规避

注入时判断：**该行绘制宽度正好是 504px 的整数倍，且下一行紧接着还是文本行**时，行尾补一个全角空格。
补一个字符后换行点前移，排版与绘制重新一致；独立成句的行不补，避免凭空多出空行。

对 57 个脚本、5602 条消息按两套算法模拟：修复前 300 条（5.4%）会压到下一句，修复后 0 条。

## 5. 其他补丁

### 5.1 点击不打断语音

文本推进 `sub_403E10` 在文字显示完后执行：

```
0x403E88  push 1 / push 0 / call ds:sndPlaySoundA   ; 停止当前语音
```

把 `0x403E88` 起 10 字节 NOP 掉即可：点击不再停语音；下一句语音由
`sub_4045D0` → `sndPlaySoundA(DATA\VOICE\xxx.wav, SND_ASYNC)` 播放，
Windows 单通道会自动顶掉上一条。BGM 走 `mciSendCommandA`，不受影响。

### 5.2 调试日志（方法记录）

排查排版问题时，曾用“新增 `.dbg` 节 + 挂钩 `sub_4027C0` 里 `0x402804` 的 `call sub_406BE0`”
的方式，把每条消息的 `y / 宽度 / 字节数` 追加写入 `dbg_msg.log`：

- 挂钩桩只在 `a8 == 255`（整句画到背景层的那一次）时记录，因此每条消息一条记录；
- 三条 `int32` 依次是 `y`（含 +32 偏移）、绘制宽度、消息字节数，可用字节数对上脚本里的句子；
- 这个调试 exe 只是临时手段，未随仓库提供。若要复现，注意 `lstrlenA` 是 stdcall，
  桩函数里不能再写 `add esp, 4`，否则栈错位、进游戏第一句话就会闪退。

## 7. 已知限制

- 取字补丁依赖 `IsDBCSLeadByte`，需在 **CP936** 区域下运行；日文区域下 GBK 的 `0xFD/0xFE` 前导会被当成单字节。
- GBK 字体只覆盖 GBK 定义的两字节码位（23940 个槽，其中 21791 个可解码），全角/半角 ASCII 沿用原版字模。
- 引擎的 `0xA000..0xDFFF` 码段在原版就是未实现分支（把颜色值当字形序号），补丁后统一走 GBK 序号，不再使用该分支。
- 排版按字节、绘制按像素的差异是引擎固有的；文本层只能通过“每行 ≤20 字”或“21 字补空格”规避。
