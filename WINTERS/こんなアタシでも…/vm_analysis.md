# 脚本 VM 与文本库分析（こんなアタシでも…）

本文是 `disassembler.py` / `assembler.py` / `opcodelist.py` / `asm_json.py` 的真值文档，结论来自
`exe\Konna.exe` 的 IDA 伪代码（`exe\Konna.pseudocode.c`）与对 `SCR.ifx` / `MSG.dat`
的逐字节验证。

## 1. 结论速览

| 项目 | 结论 |
|---|---|
| 脚本载体 | `SCR.ifx` 各条目（type 11/12/13），**不是** MSG.dat |
| 脚本单元 | 定长 **20 字节** 记录数组（无字节码变长） |
| 文本载体 | `MSG.dat`：`(start,sentences)` 索引 + 64 字节 UTF-16LE 文本槽 |
| 文本编码 | UTF-16LE |
| 文本引用 | 脚本 `MSG`/`MSG2` 指令的 P1 = 消息号；消息号 → 行区间 |
| 零突变 | 全 69 个脚本 + 完整 MSG.dat 解包→汇编后 SHA-256 与原始一致 |

## 2. 脚本记录（20 字节）

`sub_46C660`（0x46C660）的取指代码：

```
word_5EFED8 = word_55C5B8[10 * idx];   // opcode
dword_5EFEE8 = dword_55C5BC[5 * idx];  // P1
word_5EFEDA = word_55C5C0[10 * idx];   // P2
...
```

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| +0x00 | u16 | opcode | 指令号（见第 4 节） |
| +0x02 | u16 | 保留 | 恒 0 |
| +0x04 | u32 | P1 | 主参数（图片号/消息号/跳转目标等） |
| +0x08 | u16 | P2 | 次参数 |
| +0x0A | u16 | P3 | 次参数 |
| +0x0C | u16 | P4 | 次参数 |
| +0x0E | u16 | P5 | 次参数 |
| +0x10 | u16 | FLAGS | 参数解引用标志 |
| +0x12 | u16 | P6 | 次参数 |

FLAGS 位（0x46C7xx 段）：

| 位 | 作用 |
|---|---|
| bit0 / bit1 | P1 取 `word_5EED76[…]` / `word_5EF746[…]` |
| bit2 / bit3 | P2 取 `word_5EED76[…]` / `word_5EF746[…]` |
| bit4 / bit5 | P3 取 `word_5EED76[…]` / `word_5EF746[…]` |
| bit6 / bit7 | P4 取 `word_5EED76[…]` / `word_5EF746[…]` |
| bit8 / bit9 | P5 取 `word_5EED76[…]` / `word_5EF746[…]` |

opcode 500..599（算术/赋值）**不**套用这两张表，参数按立即数使用（0x46C7D4 的
`word_5EFED8 in [0x1F4,0x258)` 判断）。

### 2.1 地址空间

每种脚本类型在 VM 里占一个槽位：`100000 word = 200000 字节 = 10000 条记录`。

| SCR 目录 type | VM 槽位 | 记录基址 |
|---|---|---|
| 11 | 1 | 0 |
| 12 | 2 | 10000 |
| 13 | 3 | 20000 |

跳转指令的参数是**绝对记录号**（含基址）。反汇编时显示为 `loc_00042`（脚本内相对
记录 42），汇编时按 `.vmtype` 换回绝对号。

### 2.2 结束标记

每个脚本最后一条记录是固定 20 字节的结束标记：

```
ff ff 00 00 ff ff ff ff ff ff ff ff ff ff ff ff ff ff 00 00
```

即 `opcode=0xFFFF, P1=0xFFFFFFFF, P2..P5=0xFFFF, FLAGS=0xFFFF, P6=0x0000`。

## 3. 文本库 MSG.dat

### 3.1 布局

```
0x000000 ┌───────────────────────────────┐
         │ 索引表：100000 × 8 字节        │  消息号 m 的表项在 8*(m-1)
         │ (start, sentences)            │  start=起始槽位(1 起), sentences=行数
0x0C3500 ├───────────────────────────────┤
         │ 文本池：64 字节/槽             │  每槽 = 最多 32 个 UTF-16 单元 + 0 填充
         └───────────────────────────────┘
```

- 800000（0x0C3500）是游戏初始化时一次读入内存的索引区大小；文本池按需 `seek`
  `0xC3500 + (start-1)*64` 读取（0x46DA99 / 0x46DDAD 两处）。
- 索引表是**稀疏**的：只有出现过的消息号有 `(start,sentences)`，其余全 0；
  本作实际有 6634 条消息、12381 个文本槽，槽位按消息号顺序连续排列。
- 每行最多 32 个 UTF-16 单元（槽容量），但引擎逐行读取上限是 **24 字**
  （`sub_46D990` 中 `mov esi,18h` 的循环），超过会被截断。

### 3.2 消息号使用范围

剧本里 `MSG`/`MSG2` 引用的消息号：1..6624、7001..7006、10001（共 6629 个不同值），
与索引表完全吻合。`MSG` 指令 P1=0 表示关闭文本窗口。

## 5. asm.txt 语义格式

```asm
; Konna script disassembly
; file       : SCR#00200.ifx.asm.txt
; script type: 13 (VM slot 3, base record 20000)
; records    : 596
; encoding   : utf-8
; msgdb      : ...\MSG.dat

.vmtype 3

loc_00000:
    BG 289, 0, 0, 0
    WINDOW 1, 0, 0
    MSG 5443   "「・・・・・・・・・・」"
    MSG 5444   "これから先・・・真冬は変わってくれるんだろうか\n・・・"
    WAIT 2500

loc_00042:
    IF_EQ 1, 1, loc_00060
    ...
    END
```

- 标签：脚本内相对记录号，跳转目标处自动生成；普通顺序执行不插标签。
- 文本：`MSG <消息号> "<行1>\n<行2>"`，只在**首次引用**处内联定义，其他引用只写
  `MSG <消息号>`（同一消息共享同一定义，改一处即改全部引用）。
- `\n` 表示换行（每个换行 = 新的 64 字节槽）；`\"`、`\\`、`\uXXXX` 为标准转义。
- `flags=0xNNNN`：仅在 FLAGS 非 0 时出现，表示参数解引用方式。
- `RAW op, P1, P2, P3, P4, P5, flags, P6`：未知 opcode 的逐字段无损表示。

## 6. 汇编规则

- 按 asm 顺序重写 20 字节记录；`loc_xxxxx` 解析为 `base + xxxxx` 的绝对记录号。
- 文本按消息号重建 MSG.dat：所有消息按原 `start` 顺序重新排列槽位（增删行会自动
  重排并更新索引表），未在 asm 中出现的消息保持模板原样。
- 文本行超过 32 个 UTF-16 单元报错；按显示宽度超过 24 个全角字符给出“游戏会截断”的警告。
- 目录模式下按文件名里的 `#槽位号` 把脚本放回 SCR.ifx 对应槽位，重算偏移/大小，
  其它条目保持原样。

## 6.1 asm <-> JSON 文本转换（asm_json.py）

翻译流程用 `asm_json.py` 在 asm 与 JSON 之间转换，JSON 里把人名和正文分开：

```json
{
  "id": "SCR#00200.ifx#00013",
  "msg": 13,
  "ref": "loc_00006",
  "name": "真冬",
  "pre_jp": "「あっ、遠井君。それじゃまた明日ねーっ」",
  "message": "「あっ、遠井君。それじゃまた明日ねーっ」"
}
```

规则：

- **提取**：`【真冬】` 这种独占一行的说话人 → `name`；其余行去掉换行、去掉续行
  开头的布局缩进后拼成 `pre_jp` / `message`。
- **选项**：`１・絶望する\n２・絶望しない` 这种（本作共 32 组，全部两组、最长 22 全角），
  拆成**两条独立 message**（`kind="choice-1"` / `"choice-2"`，`msg` 相同、
  `id` 各自唯一），注入时按 `msg` 收齐、按 `kind` 排序后合并回
  `１・…\n２・…`；选项行不折行，超过 24 全角会警告。
- **注入**：**每行最多 22 个全角字符（含行首缩进，收尾括号并回时 23）**，纯按字数硬折行。
  `【name】` 行之后的第一行正文**不缩进**、最多 22 字；对话行（正文以
  `「`/`『`/`（` 开头，**带不带人名都算**）的续行行首补一个全角空格，因此续行正文最多
  21 字、整行仍是 22；旁白等非对话段落不加缩进、每行 22 字。
  **例外**：收尾括号 `」`/`』`/`）` 不允许独占一行——折完若只剩它单独一行，就并回
  上一行（该行允许到 23 字，仍不超过引擎单行上限）。
- 未翻译的条目（`message == pre_jp` 且 `name` 未改）原样保留，保证 asm 往返逐字节一致。
- `message` 里手写的 `\n` 视为手动断行，原样保留（不再自动折行/加缩进）。

选项在 JSON / TSV 里的样子：

```json
{"id":"SCR#00204.ifx#00091","msg":5967,"ref":"loc_00000","kind":"choice-1",
 "pre_jp":"もう・・つきあいたくない","message":"もう・・つきあいたくない","width":12.0}
{"id":"SCR#00204.ifx#00092","msg":5967,"ref":"loc_00000","kind":"choice-2",
 "pre_jp":"それでも、つきあっていきたい","message":"それでも、つきあっていきたい","width":14.0}
```

```text
SCR#00204.ifx#00091	5967		もう・・つきあいたくない
SCR#00204.ifx#00092	5967		それでも、つきあっていきたい
```

例：

```asm
    MSG 13   "【真冬】\n「哎呀，远井同学。那么明天见啦——」这是一段\n　特意写得很长的中文译文，用来测试自动折行是\n　否按二十三个全角字符来断。"
```

## 7. 验证结果

| 项目 | 结果 |
|---|---|
| 反汇编 69 个脚本 → 汇编 | SCR.ifx SHA-256 与原始一致（`940f5b92…46dee`） |
| MSG.dat 读入 → 重建 | SHA-256 与原始一致（`420192485eda638c…16e682`） |
| 单脚本（`SCR#00200.ifx`）反汇编 → 汇编 | 逐字节一致 |
| 修改一条消息文本（变长） | 重新反汇编回读一致，其它消息文本不变 |
| 增加一行（行数变化） | 索引表/文本池自动重排，MSG.dat 增大 64 字节，其余消息不受影响 |
| asm → JSON 提取 → 原样注入 | 69 个 asm 逐字节一致 |
| 翻译注入（超长中文 + 人名） | 每行 22 全角（收尾括号并回时 23）��回装后 MSG.dat/SCR.ifx 正常，回读一致 |

## 8. 已知限制

1. 281（CHOICE）只出现 1 次，语义靠上下文推断，未完全确认。
2. `word_5EED76` / `word_5EF746` 两张变量表的含义未完全展开（只按 FLAGS 原样保留）。
3. 401/411/412 等演出指令只确认了调用点，未逐个还原参数语义。
4. 文本行超过 24 字时游戏会截断，工具只能警告，不能改变引擎行为。
5. 未做游戏内实测（需要把重建后的 SCR.ifx / MSG.dat 放进游戏目录运行）。
